# Лабораторная работа №3. Декомпозиция и проектирование микросервисной системы
## Предметная область: Управление грузоперевозками для малых транспортных компаний

### 1. Описание предметной области, акторы, пользовательские сценарии

**Описание:** Система автоматизирует полный цикл грузоперевозки: от заявки клиента до закрытия заказа и финансового расчёта. Ориентирована на небольшие транспортные компании и экспедиторов, которые ведут бизнес в «полуавтоматическом» режиме и нуждаются в прозрачном отслеживании и снижении ручной работы.

**Акторы:**
- **Клиент** – юридическое или физическое лицо, заказывающее перевозку.
- **Диспетчер** – сотрудник компании, назначающий транспорт и водителя.
- **Водитель** – исполнитель перевозки, передающий координаты и статусы.
- **Бухгалтер** – сотрудник, контролирующий выставление счетов и оплату.
- **Внешние системы:** платёжный шлюз, картографический сервис (для расчёта маршрутов).

**Ключевые пользовательские сценарии:**
1. *Как клиент, я хочу оставить заявку на перевозку, указав точки погрузки/разгрузки и характер груза, чтобы получить расчёт стоимости и сроков.*
2. *Как диспетчер, я хочу видеть свободные транспортные средства и назначать их на заявку, чтобы оптимизировать загрузку автопарка.*
3. *Как водитель, я хочу получать задание и отправлять геолокацию, чтобы диспетчер и клиент видели прогресс.*
4. *Как бухгалтер, я хочу автоматически получать счета после завершения перевозки, чтобы выставлять их клиенту и контролировать оплату.*
5. *Как клиент, я хочу получать уведомления о статусе перевозки (назначен водитель, в пути, доставлено), чтобы планировать свои процессы.*

**Доменные события (Event Storming):**
- `ЗаявкаСоздана` (OrderCreated)
- `МаршрутРассчитан` (RouteCalculated)
- `ВодительНазначен` (DriverAssigned)
- `ДокументыСформированы` (DocumentsGenerated)
- `ПеревозкаНачата` (ShipmentStarted)
- `ГрузДоставлен` (DeliveryCompleted)
- `СчётВыставлен` (InvoiceCreated)
- `ОплатаПолучена` (PaymentReceived)
- `ЗаказЗакрыт` (OrderClosed)

### 2. Доменные события и ограниченные контексты с глоссариями

| Ограниченный контекст | Сервис | Ключевые термины (глоссарий) |
|-----------------------|--------|-------------------------------|
| Управление заказами | `order-service` | **Заявка** – запрос клиента на перевозку с уникальным номером. **Статус заказа** – текущее состояние (NEW, ROUTE_CALCULATED, ASSIGNED, IN_TRANSIT, DELIVERED, INVOICED, PAID, CLOSED). **Сага** – последовательность шагов с компенсациями. |
| Маршрутизация и тарификация | `routing-service` | **Маршрут** – оптимальный путь между точками. **Стоимость** – цена перевозки, рассчитанная по тарифам. **Геозона** – область для расчёта дополнительных сборов. |
| Диспетчеризация и автопарк | `dispatch-service` | **Водитель** – сотрудник с правами и доступностью. **Транспортное средство** – грузовик с характеристиками. **Назначение** – связка заказа с водителем и ТС. |
| Документооборот | `document-service` | **Транспортная накладная** – основной перевозочный документ. **Путевой лист** – документ учёта работы водителя. **Шаблон** – форма для генерации PDF. |
| Отслеживание | `tracking-service` | **Координаты** – широта/долгота ТС. **Событие трекинга** – факт изменения статуса (начало движения, прибытие). **Статус доставки** – актуальное состояние груза. |
| Финансовые расчёты | `settlement-service` | **Счёт** – документ на оплату. **Платёж** – поступление денег. **Начисление** – сумма к оплате. **Акт** – документ о выполненных работах. |
| Уведомления | `notification-service` | **Уведомление** – сообщение, отправленное клиенту/водителю. **Канал** – email, SMS, push. **Шаблон** – заготовка текста. |

### 3. Карточки сервисов и отвергнутые варианты разбиения

#### 3.1. `order-service` (Оркестратор саги)
| Поле | Значение |
|------|----------|
| **Название** | `order-service` |
| **Ответственность** | Управление жизненным циклом заявки, координация саги оформления и выполнения перевозки. |
| **Владеет данными** | Заявка (Order), история статусов, данные клиента (минимально необходимые). |
| **Предоставляет** | `POST /api/v1/orders`, `GET /api/v1/orders/{id}`, `PATCH /internal/v1/orders/{id}/status` (для других сервисов) |
| **Зависит от** | `routing-service` (синхронно), `dispatch-service` (синхронно), `document-service` (синхронно); подписан на события `delivery.completed`, `payment.received`, `invoice.created` |
| **Нефункциональные требования** | Высокая надёжность (критичный сервис), нагрузка до 1000 заявок/день, задержка ответа < 500 мс. |
| **Обоснование границы** | Центральный координатор саги. Выделен отдельно, чтобы другие сервисы не знали о последовательности шагов и компенсациях. |

#### 3.2. `routing-service`
| Поле | Значение |
|------|----------|
| **Название** | `routing-service` |
| **Ответственность** | Расчёт оптимального маршрута и стоимости перевозки на основе тарифов. |
| **Владеет данными** | Тарифы, геозоны, кэш маршрутов. |
| **Предоставляет** | `POST /internal/v1/route/calculate` |
| **Зависит от** | Внешний картографический сервис (синхронно), `order-service` (не зависит) |
| **Нефункциональные требования** | Высокая нагрузка на чтение (расчёт маршрутов), кэширование в Redis. Задержка < 1 с. |
| **Обоснование границы** | Разные нефункциональные требования: частота вызовов и требования к latency отличаются от других сервисов. |

#### 3.3. `dispatch-service`
| Поле | Значение |
|------|----------|
| **Название** | `dispatch-service` |
| **Ответственность** | Управление автопарком, назначение водителя и ТС на заявку. |
| **Владеет данными** | Водители, транспортные средства, назначения. |
| **Предоставляет** | `POST /internal/v1/dispatch/assign`, `GET /internal/v1/dispatch/available` |
| **Зависит от** | `order-service` (получает заказ через синхронный вызов от order-service) |
| **Нефункциональные требования** | Критичность средняя, нагрузка низкая (10–100 операций/день). |
| **Обоснование границы** | Специфическая бизнес-логика подбора ресурсов, отличная от других сервисов. |

#### 3.4. `document-service`
| Поле | Значение |
|------|----------|
| **Название** | `document-service` |
| **Ответственность** | Генерация и хранение транспортных документов (накладные, путевые листы). |
| **Владеет данными** | Документы, шаблоны, метаданные. |
| **Предоставляет** | `POST /internal/v1/documents/generate`, `GET /api/v1/documents/{id}` (клиентский доступ) |
| **Зависит от** | MinIO (объектное хранилище), `order-service` (получает данные для генерации) |
| **Нефункциональные требования** | Долговременное хранение, низкая нагрузка, требования к аудиту. |
| **Обоснование границы** | Специфические требования к хранению бинарных данных и юридической значимости документов. |

#### 3.5. `tracking-service`
| Поле | Значение |
|------|----------|
| **Название** | `tracking-service` |
| **Ответственность** | Приём и хранение координат ТС, отслеживание статуса доставки, публикация событий. |
| **Владеет данными** | Треки, события трекинга, текущие статусы. |
| **Предоставляет** | `POST /internal/v1/tracking/location`, `GET /api/v1/tracking/{orderId}` (клиентский доступ) |
| **Зависит от** | `order-service` (получает заказ при старте перевозки), RabbitMQ |
| **Нефункциональные требования** | Высокая частота записи (координаты каждые 30 сек), требования к геоданным. |
| **Обоснование границы** | Отдельный тип данных (геоданные) и высокие требования к записи. |

#### 3.6. `settlement-service`
| Поле | Значение |
|------|----------|
| **Название** | `settlement-service` |
| **Ответственность** | Выставление счетов, приём оплаты, финансовые расчёты. |
| **Владеет данными** | Счета, платежи, начисления. |
| **Предоставляет** | `POST /internal/v1/invoices`, `POST /internal/v1/payments` (webhook от платёжного шлюза) |
| **Зависит от** | Внешний платёжный шлюз, RabbitMQ (события `delivery.completed`) |
| **Нефункциональные требования** | Высокие требования к аудиту и безопасности, низкая нагрузка. |
| **Обоснование границы** | Интеграция с внешней финансовой системой и отдельные требования к аудиту. |

#### 3.7. `notification-service`
| Поле | Значение |
|------|----------|
| **Название** | `notification-service` |
| **Ответственность** | Отправка уведомлений клиентам и водителям по различным каналам. |
| **Владеет данными** | История уведомлений, шаблоны. |
| **Предоставляет** | Только подписка на события (нет публичного API) |
| **Зависит от** | RabbitMQ, внешние провайдеры (SMS, email) |
| **Нефункциональные требования** | Низкая критичность, асинхронная работа, не влияет на основной сценарий. |
| **Обоснование границы** | Сбой уведомлений не должен ломать перевозку, поэтому выделен в отдельный сервис с асинхронным взаимодействием. |

**Отвергнутые альтернативы:**
- **Объединение `order-service` и `dispatch-service`:** Отказались, так как диспетчеризация имеет собственную сложную логику подбора и может развиваться независимо.
- **Объединение `document-service` и `settlement-service`:** Разные требования к хранению и аудиту; документы — это бинарные файлы, финансы — строгие транзакции.
- **Выделение `user-service`:** Аутентификация и авторизация выполняются Keycloak, поэтому отдельный сервис пользователей не требуется.

### 4. Таблица выбранного ПО с обоснованием

| Компонент | Кто использует | Обоснование |
|-----------|----------------|-------------|
| **PostgreSQL** (отдельная БД на сервис) | `order-service`, `routing-service`, `dispatch-service`, `document-service`, `tracking-service`, `settlement-service` | Транзакции и связи между сущностями (заказы, счета, водители). |

| **MinIO** | `document-service` | Хранение PDF-документов и шаблонов (S3-совместимое объектное хранилище). |
| **Keycloak** | API Gateway | Аутентификация и авторизация по OAuth 2.0 / OpenID Connect. |
| **API Gateway** (Spring Cloud Gateway или Nginx) | Клиент | Единая точка входа, маршрутизация, проверка JWT, rate limiting. |

### 5. Архитектурная схема, диаграммы последовательности, таблица взаимодействий

#### 5.1. Архитектурная схема (см. `docs/architecture.drawio` и `docs/architecture.png`)

**Описание:** Клиент (веб/мобильное) обращается только через API Gateway. Gateway проверяет JWT через Keycloak и маршрутизирует запросы в `order-service`. `order-service` синхронно вызывает `routing-service`, `dispatch-service`, `document-service`. Асинхронно через RabbitMQ общаются: `order-service`, `tracking-service`, `settlement-service`, `notification-service`. У каждого сервиса своя БД (PostgreSQL), у `document-service` — MinIO. Внешние системы: картографический сервис (для `routing-service`), платёжный шлюз (для `settlement-service`).

#### 5.2. Диаграммы последовательности

- **Успешный сценарий** (`docs/sequence-success.png`): создание заявки → расчёт маршрута → назначение водителя → генерация документов → старт перевозки → доставка → выставление счёта → оплата → закрытие заказа.
- **Сценарий со сбоем** (`docs/sequence-failure.png`): сбой на шаге оплаты (или таймаут). Показаны компенсирующие действия: `order-service` переводит заказ в статус `PAYMENT_FAILED`, уведомляет клиента, при необходимости инициирует возврат (если оплата уже прошла, но заказ отменён).

#### 5.3. Таблица взаимодействий

| № | Инициатор → получатель | Тип | Эндпоинт или событие | Назначение |
|---|------------------------|-----|----------------------|------------|
| 1 | Клиент → API Gateway → `order-service` | sync | `POST /api/v1/orders` | Создание заявки |
| 2 | `order-service` → `routing-service` | sync | `POST /internal/v1/route/calculate` | Расчёт маршрута и стоимости |
| 3 | `order-service` → `dispatch-service` | sync | `POST /internal/v1/dispatch/assign` | Назначение водителя и ТС |
| 4 | `order-service` → `document-service` | sync | `POST /internal/v1/documents/generate` | Генерация документов |
| 5 | `order-service` → RabbitMQ | async | `order.status.changed` | Уведомление о смене статуса (подписчики: `tracking-service`, `notification-service`) |
| 6 | `tracking-service` → RabbitMQ | async | `delivery.completed` | Завершение доставки (подписчики: `order-service`, `settlement-service`) |
| 7 | `settlement-service` → RabbitMQ | async | `invoice.created` | Счёт выставлен (подписчики: `order-service`, `notification-service`) |
| 8 | `settlement-service` → RabbitMQ | async | `payment.received` | Оплата получена (подписчики: `order-service`, `notification-service`) |
| 9 | `tracking-service` → `order-service` | sync | `PATCH /internal/v1/orders/{id}/status` | Обновление статуса (опционально, если требуется немедленная реакция) |

### 6. Перечень событий (RabbitMQ)

| Топик / очередь | Издатель | Подписчики | Структура сообщения |
|-----------------|----------|------------|---------------------|
| `order.status.changed` | `order-service` | `tracking-service`, `notification-service` | `{ eventId, eventType, occurredAt, schemaVersion, payload: { orderId, oldStatus, newStatus } }` |
| `delivery.completed` | `tracking-service` | `order-service`, `settlement-service` | `{ eventId, eventType, occurredAt, schemaVersion, payload: { orderId, completedAt, actualRoute } }` |
| `invoice.created` | `settlement-service` | `order-service`, `notification-service` | `{ eventId, eventType, occurredAt, schemaVersion, payload: { invoiceId, orderId, amount, currency } }` |
| `payment.received` | `settlement-service` | `order-service`, `notification-service` | `{ eventId, eventType, occurredAt, schemaVersion, payload: { paymentId, invoiceId, amount, currency } }` |
| `payment.failed` | `settlement-service` | `order-service`, `notification-service` | `{ eventId, eventType, occurredAt, schemaVersion, payload: { invoiceId, orderId, reason } }` |

**Требования к событиям:** у каждого события есть `eventId` (UUID) для идемпотентности, `schemaVersion` для эволюции схемы, `occurredAt` в UTC. Обработчики должны игнорировать повторно доставленные сообщения (проверка по `eventId`).

### Примечание по саге

Сага оркестрируется `order-service`. Шаги: создание заявки → расчёт маршрута → назначение водителя → генерация документов → старт перевозки → доставка → выставление счёта → оплата → закрытие.

**Компенсирующие действия при сбое на шаге оплаты:**
- Если оплата не поступила в течение заданного времени, `order-service` переводит заказ в статус `PAYMENT_OVERDUE`, уведомляет клиента.
- Если оплата отклонена (`payment.failed`), заказ переводится в `PAYMENT_FAILED`, инициируется повторная попытка или эскалация к бухгалтеру.
- Поскольку груз уже доставлен, откатить перевозку нельзя, поэтому компенсация заключается в финансовых корректировках (возврат средств, изменение счёта) и уведомлениях.
